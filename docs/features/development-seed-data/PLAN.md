# Development Seed Data Plan

## Status

Implementation and review are complete. The user confirmed successful seed execution and approved Milestone 2 on 2026-08-23. The agent did not independently observe the live command output or database row counts.

## Goal

Add small, repeatable development seed commands for the implemented `identity-access` and `room-catalog` modules.

The seed data must be sufficient for manual API checks of sign-in, RBAC, public room type queries, staff room queries, management queries, facility relationships, and room status filters.

## Scope

The implementation will add one seed file per module:

- `src/database/seeds/identity-access.seed.ts`
- `src/database/seeds/room-catalog.seed.ts`

Each file will be independently executable through a module-specific package script. A convenience `seed` package script will run both module scripts in sequence without introducing a third source entrypoint.

Both seed commands will:

- Use the existing PostgreSQL `AppDataSource` and module-owned TypeORM entities.
- Require the database schema to be migrated before seeding.
- Refuse to run when `NODE_ENV` is `production`.
- Write all missing rows for their module in a separate database transaction.
- Find existing rows by stable natural keys and skip compatible rows, so a second run does not create duplicates.
- Fail on conflicting existing seed keys instead of overwriting user data.
- Close the data source on both success and failure.
- Print a short summary without printing the password, password hash, or tokens.

The Identity Access seed will additionally:

- Read the shared account password from `SEED_ACCOUNT_PASSWORD`.
- Validate that the seed password is between 8 and 30 characters.
- Hash the password with the existing Argon2id adapter.

## Implementation Design

Each module seed file will keep its small data definitions near its execution logic. The implementation will not introduce a seeding framework, Nest application bootstrap, command framework, factories, fixture library, or shared orchestration source file.

The Identity Access seed transaction will create missing accounts.

Execution order inside the Room Catalog seed transaction will be:

1. Create or resolve facilities by name.
2. Create or resolve room types by code.
3. Create missing room type facility relationships.
4. Create missing rooms by room number.

Identity account creation will use the existing domain model and persistence mapper before saving `AccountOrmEntity`. Room Catalog seed rows will use its TypeORM entities directly because that module follows the standard layered structure.

The seed scripts will not call HTTP endpoints, application authentication handlers, or room management services. Those paths contain user workflow behavior that is unnecessary for deterministic development setup.

## Configuration and Documentation

- Add `SEED_ACCOUNT_PASSWORD` to `.env.example` with no real credential value.
- Add `seed:identity` and `seed:room-catalog` scripts to `package.json`.
- Add a convenience `seed` script that runs both module scripts in sequence.
- Add a short README section that states the required migration command, password variable, individual and combined seed commands, seeded emails, development-only restriction, and idempotent behavior.
- Do not add seed configuration to the application-wide Joi schema because the normal API process does not require this variable. The seed entrypoint validates it independently.

## Error Handling

The applicable module seed command must exit unsuccessfully with a concise message when:

- It is run with `NODE_ENV=production`.
- The Identity Access seed receives a missing or invalid `SEED_ACCOUNT_PASSWORD`.
- Database initialization fails.
- Required migrated tables are unavailable.
- An existing natural key conflicts with the expected seed record.
- Any transactional write fails.

Raw credentials and complete database error objects must not be logged.

## Verification Strategy

No E2E suite or new seeding framework is required for this small development utility.

Implementation verification will include:

- Prettier checks for every changed source and documentation file.
- ESLint for both seed source files.
- The repository-local Nest build.
- `git diff --check`.
- A run of each module seed against a dedicated migrated PostgreSQL development or test database.
- A second run of each module seed against the same database to confirm no duplicate rows are created.
- Focused queries that confirm 6 accounts, 5 facilities, 3 room types, 8 facility assignments, and 6 rooms exist with the planned roles, lifecycle states, and relationships.

Database verification must never target a production database. If a suitable local PostgreSQL database is unavailable during implementation, record that verification as pending instead of claiming it passed.
