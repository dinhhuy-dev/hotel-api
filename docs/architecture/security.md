# Security

## 1. Security Model

The `identity-access` module owns accounts, credentials, sessions, roles, and role-to-capability assignments. Other modules own their resource-level security rules.

Every request uses an immutable security context containing the authenticated account ID, session ID, roles, resolved capabilities, and correlation ID. Roles or account identifiers supplied in request bodies, query parameters, events, or client headers are never trusted as the current actor.

Security is enforced in this order:

1. Authenticate the session.
2. Resolve active roles and capabilities.
3. Check the required RBAC capability.
4. Enforce resource ownership, task assignment, and business security invariants inside the application use case.

Access is denied by default.

## 2. Authentication

### 2.1 Credentials

- Passwords are hashed with Argon2id using at least 19 MiB of memory, two iterations, and one degree of parallelism. Higher parameters are selected after deployment benchmarking.
- Each password uses a unique salt generated by the hashing library.
- Passwords are never encrypted, stored in plain text, logged, or included in events.
- Password verification upgrades an outdated hash after a successful login.
- Passwords contain at least 15 characters when no additional authentication factor is required. The maximum accepted length is at least 64 characters.
- Passwords support long passphrases, Unicode, and whitespace without silent truncation or character-composition rules.
- Password policy rejects common and known-compromised passwords and does not require periodic changes without evidence of compromise.
- Login, recovery, and account-registration responses do not reveal whether an account exists.
- Login attempts are throttled by both account identifier and source context. Temporary throttling must not create a permanent account-denial attack.

Password-reset tokens are cryptographically random, single-use, short-lived, and stored as hashes. A successful password reset revokes existing refresh sessions and sends a security notification without including the password.

### 2.2 Access Tokens

Access tokens are short-lived signed JWTs. They contain only authorization and session identifiers, not customer profiles or sensitive data.

Required claims are:

| Claim         | Meaning                         |
| ------------- | ------------------------------- |
| `iss`         | Trusted token issuer            |
| `aud`         | Hotel API audience              |
| `sub`         | Account identifier              |
| `jti`         | Unique token identifier         |
| `sid`         | Server-side session identifier  |
| `roles`       | Active role codes at issue time |
| `authVersion` | Account security version        |
| `tokenType`   | `access`                        |
| `iat`         | Issue time                      |
| `nbf`         | Earliest valid time             |
| `exp`         | Expiration time                 |

Token verification uses an explicit algorithm allowlist and validates the signature, issuer, audience, token type, validity times, and required claims. Unsigned tokens and algorithms selected only from the token header are rejected.

### 2.3 Refresh Tokens and Sessions

Refresh tokens are longer-lived signed JWTs bound to one server-side session and one client context. Their claims identify the account, session, token family, unique token, token type, issue time, and expiration.

- Refresh tokens are rotated on every successful refresh.
- The previous refresh token is invalidated while its family relationship is retained.
- Reuse of an invalidated refresh token revokes the complete token family and records a security event.
- Only a hash of the active refresh token identifier or token value is stored.
- Refresh sessions have absolute expiration and may also enforce inactivity expiration.
- Access-token lifetime is always shorter than refresh-session lifetime.
- Token lifetimes are validated configuration values.

For browser clients, refresh tokens are sent only in `HttpOnly`, `Secure`, appropriately scoped `SameSite` cookies. Cookie-based refresh and logout endpoints use CSRF protection and origin validation. Authentication tokens must not be returned in URLs or written to browser-accessible logs.

### 2.4 Session Revocation

- Logout revokes the current refresh session and denies the current access-token `jti` until its expiration.
- Logout-all, password reset, account disablement, and credential compromise revoke every session for the account.
- Role or capability changes increment `authVersion` and invalidate tokens issued with an older version.
- Disabled or locked accounts cannot log in, refresh, or use a session.
- Signing keys support rotation through key identifiers without accepting unknown or retired keys beyond their controlled overlap period.

## 3. Role-Based Access Control

A role is a named set of capabilities. Users receive capabilities only through active role assignments; capabilities are not assigned directly to accounts.

The system roles are:

- `ADMINISTRATOR`
- `HOTEL_MANAGER`
- `RECEPTIONIST`
- `HOUSEKEEPING_STAFF`
- `MAINTENANCE_STAFF`
- `CUSTOMER`

An administrator may manage staff role definitions, role-to-capability mappings, and account-role assignments. System role codes remain stable. The `CUSTOMER` role and customer-only capabilities cannot be converted into staff privileges.

Access decisions use the current server-side role mappings. Capability lists supplied by a client or embedded in an older token are not authoritative. Role-mapping caches are invalidated when a mapping changes.

Users may hold multiple compatible staff roles, and their effective capabilities are the union of those roles. `CUSTOMER` is not combined with a staff role on the same account. At least one active administrator must remain in the system.

The administrator role is not an unrestricted superuser. It receives only the capabilities listed below unless another staff role is explicitly assigned.

## 4. Resource Ownership and Assignment

RBAC determines whether a role may attempt an action. The application use case determines whether the actor may act on the specific resource.

### 4.1 Customer Resources

- The customer profile is resolved from the authenticated account-to-customer link.
- Customer requests do not choose an authoritative `customerId`; the use case derives it from the security context.
- Reservation ownership is determined by the reservation's customer reference.
- Payment and invoice ownership is determined through the associated reservation.
- Customer history queries are always filtered by the authenticated customer reference.
- An identifier that is difficult to guess does not replace an ownership check.

### 4.2 Staff Assignments

- Housekeeping staff may view and update only tasks assigned to their account.
- Maintenance staff may view and update only work assigned to their account.
- Assignment is checked when a task is read and again when its state changes.
- Managers assign tasks through management capabilities; staff cannot assign work to themselves.

For private customer or assigned-task resources, an inaccessible identifier may return `404` to avoid revealing that the resource exists. A known resource operation that is denied by role returns `403`.

## 5. Enforcement Boundaries

- Authentication is global by default. Anonymous endpoints require an explicit public-route marker.
- Public endpoints are limited to login, token refresh, password recovery, optional customer registration, and room-availability search.
- A transport authentication guard verifies the token, session state, access-token denylist, and `authVersion`, then builds the security context.
- An RBAC guard performs the route-level capability check.
- The application handler performs the authoritative capability, ownership, assignment, and state checks before mutation or sensitive disclosure.
- Cross-module application calls propagate the immutable security context; they do not pass a mutable HTTP request object.
- Background work uses a dedicated system actor with a named purpose, not an administrator role.
- Integration-event actor metadata is trace information and is never accepted as new authorization proof.
- User interfaces may hide unavailable actions, but backend enforcement remains mandatory.

## 6. Sensitive Data and Transport

- Production APIs accept authenticated and sensitive requests only over TLS.
- CORS uses an explicit origin allowlist. Credentialed requests never use a wildcard origin.
- Reverse-proxy trust is configured explicitly; untrusted forwarded headers cannot determine client identity or transport security.
- Access tokens, refresh tokens, passwords, reset tokens, payment credentials, and full identification numbers are never logged.
- Identification values are minimized, masked in responses, and encrypted when retrieval of the original value is required.
- Raw payment-card data is not stored. The payment module stores provider tokens and non-sensitive transaction references only.
- Secrets and signing keys are loaded through validated secret configuration and support rotation.
- Security headers are enabled centrally for HTTP responses.

## 7. Security Events

Record structured security events for:

- Login success, login failure, and throttling.
- Password reset and credential change.
- Session creation, refresh, logout, revocation, and refresh-token reuse.
- Account enablement, disablement, and lock state changes.
- Role definition, capability mapping, and role assignment changes.
- Repeated authorization or ownership-check failures.
- Signing-key rotation and token-validation failures.

Security events include timestamp, event type, account ID when known, session ID when available, correlation ID, source context, and outcome. They never include credentials or raw tokens.

Security-event logging is technical security monitoring and does not create an `audit` business module.

## 8. Security Tests

- Every capability has allow and deny tests for its default roles.
- Custom role changes take effect only through assigned RBAC capabilities and invalidate affected sessions.
- Customer resource tests replace identifiers with another customer's identifiers and verify denial without data disclosure.
- Housekeeping and maintenance tests verify assigned and unassigned task access.
- Token tests cover invalid signatures, disallowed algorithms, issuer, audience, token type, expiration, not-before time, and security version.
- Refresh tests cover rotation, concurrent refresh, reuse detection, family revocation, logout, and logout-all.
- Authentication tests cover throttling, generic failure messages, disabled accounts, and password-reset token reuse.
- Browser refresh tests cover cookie attributes, CSRF protection, and rejected origins.
- Logs and error responses are tested for credential and sensitive-data leakage.
